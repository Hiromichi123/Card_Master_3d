## 2. 三层结构怎么落的

```
Command → BattleEngine → Resolution(events + patches + finalState)
        → PresentationDirector → Scene / HUD
```

**权威状态与显示状态是两个对象。** `applyCommand` 返回时权威状态已经是终态；
显示状态落后于它，按事件逐个推进。推进分两种，对应两类信息：

- **结构**（谁在哪个区、哪个槽）跟**事件**走；
- **数值**（HP / ATK）跟 **patch** 走，因为 patch 的 `atEventSeq` 就是命中节点。

这样「不提前显示最终 HP」不是靠纪律，而是结构上做不到——显示状态里根本没有终值可读。

### 跳过与正常为什么必然一致

显示状态**只在 beat 的 `onComplete` 里变**。而 `Timeline.skipToEnd()` 会给每个未完成的
步骤补发 `onUpdate(eased(1))` 与 `onComplete`（这是 P1 就写好的实现，不是这次加的）。
于是「跳过」只是换了一种走到同一串回调的方式，等价性是**构造性质**，不需要额外的对齐机制。

### 会话为什么是框架无关的类

`BattleScene` 在切到「数据自检」时会卸载。状态机若活在 `useState` 里，会连权威状态与输入锁
一起死掉。而 `applyCommand` 是同步返回终态的，所以放在类里，切场景最多丢**演出**，
永远丢不掉**规则**。同时导演要从 Canvas 内的 `useFrame` 拿 `tick(delta)`、HUD 要从 Canvas 外
重渲染，一个类实例是能同时接住两边的最小做法。

它不 import three / React / DOM，所以整局可以在 node 里跑完并断言——P3 风险最集中的部分
完全不需要浏览器。

## 3. 三处必须绕开的坑（都实际踩到并修掉）

### 3.1 槽位下标有两个口径

`SlotMarkers.slotKey()` 用的是 `buildSlots()` 的**全局**编号（0..25），而引擎的
`SideZones.prep` / `battle` 用的是**每侧**下标（0..7 / 0..4）。混用之后点准备槽会报
`noEmptyPrepSlot`——牌被"放到"了 12 号槽，而准备区只有 8 个。

现在 `SlotDescriptor` 同时给出 `index`（全局，只用于稳定键）与 `rowIndex`（每侧，进引擎），
`placements.ts` 的 `globalSlotIndex()` 负责换算，单测对全部 26 个槽做往返断言：
`buildSlots()` 的顺序一旦变动而没同步换算，测试立刻失败，而不是高亮悄悄亮在别人的槽上。

### 3.2 `EffectComposer` 会让之后的兄弟组件收不到 `useFrame`

P1 就记录过（见 `docs/validation/P1.md` 第 3.18 节），`BattleScene.tsx` 的注释里也点名了
「P3 的演出层也要遵守」。这次照样踩得到：`EffectSystem` 之前只挂在实验台，
战斗场景里根本没挂，`effectDirector.play()` 是个空响。

现在 Canvas 里的顺序是硬性的：`PresentationDriver` → `EffectSystem` → `PerfSampler`
→ `<PostEffects>`。而浏览器用例里那条「点结束回合之后 HUD 必须推进到第 2 回合」
同时就是这个坑的探针——静默失效的表现正是「点了没反应、且零报错」。

### 3.3 「快速」档原本比普通档慢

`SPEED_SCALE` 是**演出时长的倍数**（实验台的 `durationScale` 一直这么用），不是速度倍数。
第一版写成 `timeline.update(delta * SPEED_SCALE.fast)`，于是快速档把每帧推进的时间**乘** 0.45，
反而慢一倍多。改成除以它。测试里有一条直接断言三种档位的帧数递增关系，
就是这条抓出来的。

## 6. 顺带修掉的三处引擎缺口

这三处都是「改了状态却没发事件」。演出层只能靠事件与 patch 知道数值变了
（PLAN 第 4.1 节：「目标、数值、源实例、旧值/新值、事件序号均写入事件」），
所以显示状态会永远停在旧值。等价性测试逐个抓出来的：

| 缺口 | 现象 | 修法 |
| --- | --- | --- |
| 不死 / 复活把 `group.hp` 补满，只发 `CardMoved` | 复活回来的卡在画面上血量为 0 | 补发 `Healed`（发在 `CardMoved` 之前，治疗落在它倒下的那个槽位） |
| 不死 / 复活的牌不进弃牌堆，但与真死都只有一条 `CardDied` | 弃牌数只增不减 | 真进堆时补发 `CardMoved → discard` |
| 复活回场与打出手牌会复位冷却 | 卡面 CD 停在旧值 | 补发 `CooldownChanged` |

第三条是**先补投影才发现的**：`projectDisplay` 原本只比生命、区域与状态组，
冷却的变化路径与 HP 不同（走事件不走 patch），不显式比就没人看着它。
把 `cd` 加进投影之后立刻抓出。

另有一处已记录但**本次未动**：`reviveIfAble` 之后，死亡处理循环会把复活回来的主卡
`instance.zone` 又写回 `'discard'`（而它实际在 `zones.hand` / `zones.prep` 里）。
显示层不读 `instance.zone`（它按事件推进），所以 P3 不受影响；
但按 `instance.zone` 找牌的技能会看错。留给 P4 处理，见第 7 节。

## 7. 已知局限

1. **AI 仍然只出一张牌然后结束回合**（P2 就如此）。它不是一个有策略的对手。
2. **浏览器里没有构造空手/满槽的局面**。这两条在规则层有专门用例
   （`hasLegalPlay` 与 `endTurn` 的放行条件），HUD 的提示与按钮禁用也由它驱动，
   但「真的打到那个局面」没有在浏览器里跑过。
3. **`instance.zone` 在复活后不准**（见第 6 节末）。P3 不读它，P4 修。
5. **没有音效**。P7 的范围。
6. **每回合抽牌、部署、攻击是连在一起播的**，没有按行动切分节奏；快速档下会显得急促。
