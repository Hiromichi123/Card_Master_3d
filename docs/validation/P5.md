## 2. 抽卡：数据流与「先落盘再演出」

点下按钮到看见结果是**一条链路**：

```
operationId = store.nextOperationId()
rng = createRng(seedFrom(operationId))
await store.commitEconomic(p => planPull({...}))
  ├─ rejected   → 屏内一行提示（store 已 toast，不重复）；不演出
  ├─ saveFailed → 快照逐字节不变，按钮可再点；不演出
  └─ ok         → setRun({view})  ← 钱已扣、卡已加**且已落盘**，这才开始演出
```

采样就发生在 `commitEconomic` 的队列里（`busy` 检查与 operationId 去重之后、落盘之前），
所以「抽到哪十张」与「落盘的那笔事务」是同一个执行体。

**代价（如实记）**：演出中途硬刷新会丢演出——结果在盘上，但动画不会重放，
`lastResult` 也只在内存里。反向做（把待播结果也持久化）要动存档 schema 与迁移，
收益远小于风险，本阶段不做。

**降级出口只有一个**：`presentationSpeed === 'skip'` 时**根本不挂 3D 舞台**，结果直接出来。

## 3. 实测数字

### 3.1 经济正确性（读 IndexedDB 落盘值，不看界面文本）

| 用例 | 结果 |
| --- | --- |
| 十连 | 金币 5000 → **500**（恰好 −4500）；库存 247 → **257**（恰好 +10） |
| 单抽 | 金币 5000 → **4500**；库存 247 → **248** |
| 余额不足（A 级限定池十连要 45000） | **盘上仍然没有记录**——拒绝发生在写盘之前 |
| 抽完离开再回来 | 金币与库存不变（挂载时不重放结果，刷卡漏洞被挡住） |
| 面板列出的卡 vs 库存增量 | 逐张一致（含重复计数） |

### 3.2 概率必须现算

| 卡池 | 界面上 | 配置里手写的 `probLabel` |
| --- | --- | --- |
| 常规卡池 | **6.3%** | 8.9% |
| 特别卡池 | **100.0%** | 100%（但含义不同，见下） |

用例断言 6.3% 出现、8.9% 与「爆率」二字都不出现——渲染 `probLabel` 的实现会立刻红。

**一处容易搞错的地方**：`gacha-pools.json` 的 `computedRarePercent` 对特别卡池写的是 **94**，
界面上是 **100.0%**，**界面是对的**。那个字段按「100 分制直接求和」算，
而权重表现行规则是「按表内总和归一化」：special 表 SSS..A 有权重、B+ 及以下全 0、
总和 94，于是真实的「A 及以上」概率是 94/94。代码与用例里都写了注释。

### 3.3 3D 演出

| 项 | 结果 |
| --- | --- |
| 画布尺寸 | 1920×1034（铺满抽卡页） |
| 平均亮度 | 124（实测；断言下限 40） |
| **洋红占位像素占比** | 正常 **0**、强行让卡面 404 时 **17.8%**（断言 < 1%） |
| 画面在动 | 四帧采样至少三个不同指纹（断「演出真的在跑」，不是断静止态） |
| 控制台 | 无错误、无失败请求 |

「洋红」这条是试出来的：`AssetManager` 贴图失败的占位是洋红/黑棋盘。
先试过断「饱和度」，**方向是反的**——实测卡面 404 时饱和度反而更高（0.19 vs 0.14），
因为洋红本身很饱和；而且结果面板盖住画布之后这个数还会再掉一截，等于同时在量两件事。

演出曲线与时间表（`choreography.ts`，23 条单测）：
十连 5×2、错峰 0.075s、飞行 0.55s、翻面 0.42s（高稀有 0.72s）、
高亮卡取 `argmax(rankOf)` 且**并列取最小下标**（4 个单稀有度限定池是 100% 高稀有，
不这样会有 10 张同时要求聚焦）。「跳过 = 播完」由**采样函数无状态**保证：
把 `total` 直接传进去拿到的就是终态。

## 4. 本轮验证命令与结果

```
npm run typecheck                                  通过
npx vitest run tests/unit                          174 项通过
npx playwright test tests/browser/gacha.spec.ts     7/7 通过（22.8s）
npx playwright test tests/browser/deckEditor.spec.ts 4/4 通过
npx playwright test tests/browser/collection.spec.ts 3/3 通过
npx playwright test（全套 24 条）                    22 通过 2 失败，两条都是并行负载下的超时
```

**关于那两条失败**：`battleSlice.spec.ts` 的「普通与跳过得到完全相同」单独跑需要
**3.7 分钟**，超过 `playwright.config.ts` 的 60s 超时；`collection.spec.ts` 那条是
原「逐帧采样翻页几何」的断言在 6 个 WebGL 上下文并行时 rAF 被压得一帧都排不到
（单独跑必过）。后者已改成**不依赖帧率**的断法：
类名先后顺序（MutationObserver）+ 关键帧里声明的方向与缩放（CSSOM）。
