## 2. 抽卡：数据流与「先落盘再演出」

点下按钮到看见结果是**一条链路**：

```
operationId = store.nextOperationId()
rng = createRng(seedFrom(operationId))
await store.commitEconomic(p => planPull({...}))
  ├─ rejected   → 屏内一行提示（store 已 toast，不重复）；不演出
  ├─ saveFailed → 快照逐字节不变，按钮可再点；不演出
  └─ ok         → setRun({view})  ← 钱已扣、卡已加**且已落盘**，这才开始演出
```

采样就发生在 `commitEconomic` 的队列里（`busy` 检查与 operationId 去重之后、落盘之前），
所以「抽到哪十张」与「落盘的那笔事务」是同一个执行体。

**代价（如实记）**：演出中途硬刷新会丢演出——结果在盘上，但动画不会重放，
`lastResult` 也只在内存里。反向做（把待播结果也持久化）要动存档 schema 与迁移，
收益远小于风险，本阶段不做。

**降级出口只有一个**：`presentationSpeed === 'skip'` 时**根本不挂 3D 舞台**，结果直接出来。

### 3.2 概率必须现算

| 卡池 | 界面上 | 配置里手写的 `probLabel` |
| --- | --- | --- |
| 常规卡池 | **6.3%** | 8.9% |
| 特别卡池 | **100.0%** | 100%（但含义不同，见下） |

用例断言 6.3% 出现、8.9% 与「爆率」二字都不出现——渲染 `probLabel` 的实现会立刻红。

**一处容易搞错的地方**：`gacha-pools.json` 的 `computedRarePercent` 对特别卡池写的是 **94**，
界面上是 **100.0%**，**界面是对的**。那个字段按「100 分制直接求和」算，
而权重表现行规则是「按表内总和归一化」：special 表 SSS..A 有权重、B+ 及以下全 0、
总和 94，于是真实的「A 及以上」概率是 94/94。代码与用例里都写了注释。


**关于那两条失败**：`battleSlice.spec.ts` 的「普通与跳过得到完全相同」单独跑需要
**3.7 分钟**，超过 `playwright.config.ts` 的 60s 超时；`collection.spec.ts` 那条是
原「逐帧采样翻页几何」的断言在 6 个 WebGL 上下文并行时 rAF 被压得一帧都排不到
（单独跑必过）。后者已改成**不依赖帧率**的断法：
类名先后顺序（MutationObserver）+ 关键帧里声明的方向与缩放（CSSOM）。

## 4.5 主菜单

### 坐标：设计空间 + 整体等比缩放

旧版 `config.py` 定的是 **2880 × 1800 的设计分辨率**：
`AUTO_SCALE = min(视口宽/2880, 视口高/1800)`，`WINDOW_WIDTH = 设计宽 × AUTO_SCALE`。
也就是说**布局全部写在设计空间里**，最后整体乘一个因子——`WINDOW_WIDTH * 0.70`
这类比例的分母是那个缩放后的设计框，不是浏览器窗口。

这里照做：`.menu__stage` 是 2880×1800 的设计框，`--ui = min(100vw/2880, 100vh/1800)`，
位置用 `%`（相对设计框）、尺寸用 `calc(设计单位 * var(--ui))`。

实测（同一个版面在三种分辨率下的落点）：

| 视口 | 一级列起点 x | 按钮 | 海报 | 二级列右边缘 |
| --- | --- | --- | --- | --- |
| 2880×1800 | 2016（= 70%） | 300×50 | (1670, 1103) 1008×540 | 2676（= 93%） |
| 1920×1080 | 1306 | 180×30 | 605×324 | 1702 |
| 1280×720 | 870 | 120×20 | 403×216 | 1134 |

比例完全一致，且**在 2880 设计空间里二级列本来就放得下**（93%）——
上一版我按 1920 窗口算 `WINDOW_WIDTH * 0.70`，误判成「会越界」。

### 按钮：按 `ui/menu_button.py` 的画法

- **常态就有左右两个三角形**（20 设计单位，用该入口的代表色、alpha 62%）；
- **悬停时亮起三层同心圆角矩形**——旧版是画三层内缩的圆角矩形（不是模糊），
  透明度 100 / 70 / 40 × 脉动；这里用三段只有 spread、没有 blur 的 `box-shadow` 复现，
  脉动动画透明度（等价于旧版对 alpha 的调制）；
- 悬停时文字换成该入口颜色的描边光（旧版的四向偏移 glow）；
- **按钮没有底板**，与原版一致。

**唯一加的一层**是按钮区背后的横向压暗（`.menu__scrim` 的第二层）：
原版按钮压在**它自己的**背景图上没问题，本项目的菜单背景是高饱和插画，
不压这一道，未悬停的深色标签读不清（实测过两轮）。压暗加在背景上、不动按钮本身。

### 活动海报轮播（`ui/activity_poster.py`）

金边相框（8 设计单位金边 #c8c800、圆角 24、内边距 8）、位置 (58%, 60%)、

首尾相接、点击进入战役。海报取 manifest 里 `poster001/002`（旧版那两张活动海报）
与 3 张章节入场图，共 5 张。

实测：t=0 → `poster001`；t=5.25s 时**画布上同时有两层**（滑动中）；
t=6s → `poster002`；t=11s → `chapter_1_enter`；点击后落在战役页；控制台无错误。

## 4.6 商店（含活动商店）

常规与活动**同一块屏**，只有规格不同（`shops.json` 的 `normalShop` / `activityShop`），
所以做成一个 `kind` 参数。常规四排「神话 / 传承 / 探索 / 礼包」，活动三排
「活动精选 / 稀有兑换 / 常规兑换」（活动商店没有礼包）。

**每日刷新是怎么成立的**：货架按**当天**的日键现算（`store.todayKey()`，走存档自己的时钟，
所以开发期的 `?day=` 也管用），而售罄标识 `entryId` 里**自带那个日键**——
跨日之后新货架用新日键，昨天那批标识自然一个都匹配不上，货架「自己就刷新了」，
不需要迁移或清理。用例断的就是这句话的两半：**同一天两次打开货架一模一样，
换一天整批换掉**。

**购买**：`planPurchase` 把「扣钱 + 发货 + 标售罄」打成同一笔事务，
经 `commitEconomic` 落盘成功才更新界面。实测（读 IndexedDB）：
买一件 1900 金币的卡 → 金币 5000 → **3100**、库存 **247 → 248**、售罄列表多出该 `entryId`；
买不起的（551 水晶的 SSS，新号只有 300 水晶）→ **盘上仍然没有记录**（拒绝发生在写盘之前）。

**顺手补的一处导入缺陷**：活动商店的 `priceByRarity` 是**裸数字**（`{"#elna": 1080}`），
常规商店是 `{currency, amount}`。直接用会让 `price.amount` 变成 `undefined`——
界面显示「undefined」、购买校验拿 `undefined` 比大小（永远为假）而且**不报错**。
数据层按该商店自己的 `unknownRarityFallback.currency`（`badge`）补上货币，
与「徽章是活动商店用的」这条既有约定一致。

## 4.7 二级菜单：选择对战模式与限时活动模式

两层都照旧版：**主菜单「进入战斗」→ 选择对战模式**（`battle_menu.py`），
**「活动入口」→ 限时活动模式**（`activity/activity_scene.py`）——**活动商店在活动大厅里**，
不是主菜单直接进（这是我上一版接错的地方）。

三个菜单的外壳（视差背景、2880×1800 设计框、金色标题、货币与等级、入口按钮）
抽成了 `MenuChrome`：旧版是三个场景各写一遍，但外壳完全一样，
各写一遍的代价是「三处的比例迟早有一处先漂掉」。

三处参数按旧版各不相同，用 CSS 变量传给共用的样式：

| | 列 x | 列 y | 按钮 | 阶梯 | 标题 |
| --- | --- | --- | --- | --- | --- |
| 主菜单 | 70% | 25% | 300×50 | 30 | 96 |
| 选择对战模式 | **75%** | 25% | 480×50 | 30 | 96 |
| 限时活动模式 | **80%** | **30%** | 320×58 | **20** | 86 |

活动大厅另有左侧三张特性卡（宽 45%、高 10%、起点 (15%, 28%)、间隔 4%），
内容与旧版一致：迷宫挑战 / 深渊挑战（未开放）/ 协力突袭（未开放）。

**两处不能照搬，都对应本项目的既定范围**：

- 对战菜单的两条「局域网」旧版走联机房间。PLAN 第 6 节明确「UI 不提供冒充联机的入口」，
  所以保留位置、点了给出理由（提示里直接引 PLAN 第 6 节），不开假房间；
- 「本地 任选对战（双人）」要 Draft（P6），同样先给提示。

**一处按实测改的尺寸**：旧版按钮宽 300（按它自己的字号定的），
而这里最长的标签「本地 任选对战（双人）」在 40 设计单位的字号下约 480——
不加宽的话 CSS 会折行、第二行压到下一个按钮上（实测就是这样）。
现在这一列统一 480，**长度仍然一致**，另加 `white-space: nowrap` 保证任何标签都不折行
（旧版是渲染一行、超出就溢出，从不折行）。

## 4.8 换屏黑场（照旧版 `ui/transition.py`）

旧版是「每秒 800 个 alpha」，一程 255/800 ≈ **0.32 秒**：淡出到全黑 → 切屏幕 → 淡入。
这里同一个节奏，`prefers-reduced-motion` 或设置里的「静止」开着时**直接切**，不黑场。

实测（点导航栏切到图鉴，逐帧读黑场的不透明度）：
`0.00 → 0.10 → 0.31 → 0.52 → 0.73 → 0.89 → 0.52 → 0.31 → 0.10 → 0.00`——
先单调升到接近全黑、换屏后再单调落回透明 ✓。

一处与旧版不同：**换屏的瞬间就放开输入**，不等淡入走完。旧版转场期间一律不响应，
照搬的话屏幕已经能看清了还点不动（实测很别扭）。淡入被下一次跳转打断是可接受的：
黑场从当前不透明度继续往 1 走，看起来就是又黑了一次。

版面：标题 11% / 副标题 16% / 左栏 (4%, 18%, 62%×78%) / 右栏 (66%+26, 18%, 其余×78%)，
右上角一颗常亮的「返回主菜单」。每张卡是「卡名在上、稀有度描边的卡图、下方价格按钮」，
售罄时盖「已售罄」并禁用价格按钮。

**行情图**是旧版的装饰性图表（`_generate_price_history` 每次进场用 `random` 现生成）。
这里保留观感，但**按日键取种子**：同一天进来看到的是同一张图，
换一天才换行情——与货架的「每日刷新」同一套口径；旧版每次进场图都在跳。

**2026-10-07 的三处订正（用户报的）**：

1. **卡位居中、间隔平均。** 旧版 `_draw_card_offer` 的排法是
   `space = max(16*UI_SCALE, (rect.width - 总宽) / (张数 + 1))`——首尾也各留一个 `space`，
   正是 CSS 的 `space-evenly`。改成它之后**必须把 `gap` 去掉**：`gap` 只加在卡与卡之间，
   首尾拿不到，实测 1280×720 下卡间间隔比首尾边距大 **6.4px**。最密的一排（5 张 × 200 单位）
   占 1000 单位、排面约 1753 单位，余量够，不会挤到贴住。特典卡包那一排同理。
2. **卡包要画卡背。** 旧版 `_draw_pack_offer` 先垫一层会呼吸的稀有度色椭圆，再把
   `assets/ui/card_back.png` 缩到牌位上。前一版只画了光晕、把图漏了，于是右侧三个卡包是
   三个空框；现在 `<img>` 用 manifest 的 `shared.cardBack`（与 3D 卡牌同一张卡背）。
3. **玩家状态统一成一块面板**（头像 + 等级 + 经验 + 资源，头像取原项目的 `assets/ui/avatar.jpg`），
   主菜单标题下那行「当前出战：…」拿掉。组件与实测见 `docs/validation/P1.md` 第 3.12 节的
   2026-10-07 更新。

**两处按实测改的**：

- 固定高度给「排面板」而不是整排：旧版的 `spec["height"]` 量的就是面板，标签画在它上方之外。
  第一版把固定高度给了整排，面板里放不下的部分溢出去、正好被下一排的标签压住，
  点价格按钮点到的是那个标签（用例发现的）；
- 折线图的横轴刻度改成 **DOM 行**：SVG 用 `preserveAspectRatio="none"` 铺满容器，
  文字会被一起横向拉长成方块（实测「周一」就是几个色块）。

## 4.10 单人战役

旧版是两层地图（`scenes/map/world_map_scene.py` + `chapter_map_scene.py`），这里做成
一块屏的两个层（路由只有 `campaign`，ESC 从章节地图退回世界地图）：

- **世界地图**：标题 @15%、副标题「点击章节进入关卡」、章节海报横排在 (15%~75%, 62%)、
  右侧 (70%, 18%, 26%×68%) 是所选章节的详情、左下「返回上一级」；
- **章节地图**：标题 @12%、副标题「选择关卡（ESC 返回世界地图）」、
  关卡海报从左下往右上阶梯排、右侧详情给出奖励与敌方牌组、底部「已通关 N / 12 关」。

**交互照旧版**：悬停就选中（右侧详情跟着换）、点击进入/开战；
详情栏里的「进入章节 / 出战」是同一件事的显式入口。

**空章节不上地图**：`stages.json` 里有第 4 章「月之都」，但它一关都没有
（`emptyChapters` 另记着「第四章无关卡」）。列出来只会让人点进一个空地图，
清单对这条的要求也是「不构造新内容」，所以过滤掉。

### 完整循环的实测

打完 1-1（跳过 + 自动演示）后读 IndexedDB：

| 项 | 结果 |
| --- | --- |
| 结果面板的结算明细 | 金币 +300 / 经验 +100 / 本次没有掉落卡牌 |
| 存档金币 | 5000 → **5300**（恰好 +300） |
| 通关记录 | `clearedStages` = **["1-1"]** |
| 已结算 | `settledBattleIds` **恰好 1 条**（同一局只结算一次） |
| 回到地图 | 那一关盖上了「已通关」 |

奖励数字、存档货币、通关记录三者一致——因为**面板上显示的就是已经落盘的那一份**
（`App` 在进入结果态时提交事务，拿到视图才传给面板）。

**一处只在重打时才会出现的坑**：`battleId` 由 `stageId#revision@launchSeq` 拼成，
第一版把 `launchSeq` 写死成 1——第一次挑战之后存档 revision 变了还好，
但**输了重打**时 revision 没变，会撞上同一个 `battleId`，赢了也不发奖。
现在每次点「出战」都递增。

## 5. 已知限制与未完成

- **保底 / 抽数统计没做**：`GachaState.pullsByPool` 至今**没有任何写入方**，
  `EconomyTransaction` 里也没有对应字段。要做需先扩事务类型与存档 schema。
- **多卡组管理没做**：配置页只编辑当前出战卡组；`profile.decks` 结构支持多份，
  但界面不给新建/重命名/删除/切换。
- **音效**全项目都没有，计划在 P7 统一做。
- **演出会在硬刷新时丢掉**（见 2 节的取舍）。
- `EffectRecipe.cameraShake` 仍然没有消费者；抽卡的镜头震动由编排层自己按爆点强度算。
- **还没做的入口**：主菜单的融合 / Draft / 迷宫，对战菜单的两条局域网与本地双人，
  活动大厅的迷宫挑战（P6）。现在都是「能点、点了弹一句提示」，
  不是灰色禁用按钮——旧版 `_show_feature_notice` 就是这么处理未实现入口的。
- **设置页仍是占位屏**（画质/台面/视角/演出/震动/静止现在在**战斗界面**的「战斗设置」里，
  抬头只剩导航与性能读数且可收起——见 `docs/validation/P1.md` 第 3.12 节的 2026-10-07 更新）；
- **存档导入 / 导出还没做**（P5 还剩的三条：新版 JSON 导入导出、旧 `inventory/profile/deck`
  导入预览、导入的边界用例）。`domain/progression/legacyImport.ts` 里的纯逻辑已经有了；
- **演示存档与用户进度没有分开**：本项目只有一个存档，开号即拥有全部卡（`profileStore.ts`
  的临时便利设定），「重置存档」是唯一的出口。P5 验收里「演示存档与用户进度分开」这条
  **按字面还没满足**，留待决定要不要两套存档。
- **活动商店需要徽章**，而徽章只能从活动里拿——活动本身还没做，
  所以新号在活动商店里什么都买不起（用例把这条当预期行为断言下来了）。
- **售罄标识会一直累积**：每天至多十几条，一年约几十 KB。要清掉得给
  `EconomyTransaction` 加一个「商店日键」字段，属于存档 schema 变更。
- P5 整体验收（「从抽卡至组卡、通关、领奖、再购买形成完整循环」）**还不成立**：
  战役与结算、设置页仍是占位符。
